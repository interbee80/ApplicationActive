# Архитектура ApplicationActive

## Состав решения

| Проект | Назначение |
|---|---|
| `src\AppActive.Core` | ядро: модели, схема SQLite, репозитории, накопитель активности, оценка критического времени, Workflow-движок, сборка ответов Web-панели |
| `src\AppActive.Service` | служба Windows: супервизор сеансов, приём отчётов, REST API, Web-панель (статика), журналирование, обслуживание базы |
| `src\AppActive.Agent` | агент сеанса: крючок активного окна + опрос простоя, отправка отчётов службе |
| `scripts\` | сборка, установка, удаление и проверка состояния службы |
| `docs\API.md` | контракт REST API |
| `src\AppActive.Service\wwwroot` | Web-панель (HTML/CSS/JS без внешних зависимостей) |

## Почему агент на каждый сеанс

Служба работает от имени SYSTEM в сеансе 0. `GetForegroundWindow` и `GetLastInputInfo` возвращают данные
**своего** рабочего стола и **своего** сеанса, поэтому служба физически не видит активное окно
и ввод пользователя. Поэтому служба:

1. перечисляет сеансы через WTS API (`WTSEnumerateSessions`);
2. для активных сеансов получает токен пользователя (`WTSQueryUserToken`), дублирует его
   (`DuplicateTokenEx`) и запускает процесс агента в этом сеансе (`CreateProcessAsUser`;
   резервно — `CreateProcessWithTokenW`);
3. следит за живостью агента по времени последнего отчёта и перезапускает зависшие;
4. при остановке службы завершает все запущенные агенты.

Для этого службе нужны привилегии `SeTcbPrivilege`, `SeAssignPrimaryTokenPrivilege`,
`SeIncreaseQuotaPrivilege`, `SeImpersonatePrivilege` — они есть у LocalSystem, служба включает их при старте.

В консольном режиме без прав SYSTEM (отладка) агент запускается обычным способом в текущем сеансе —
конвейер «окно → агент → база → панель» проверяется полностью, кроме самого запуска от имени другого
пользователя.

## Поток данных

1. **Агент** держит крючок `EVENT_SYSTEM_FOREGROUND` (точные моменты переключения окон) и таймер
   с интервалом опроса. На каждом такте он собирает отрезки «окно было активным» и по времени последнего
   ввода (`GetLastInputInfo`) вычисляет активные секунды (см. `ActivityMath`).
2. Отчёт уходит по HTTP на loopback-адрес службы (`POST /api/ingest/report`) с ключом агента.
   В ответ служба возвращает текущие настройки, поэтому смена интервала опроса в панели применяется
   в течение одного такта.
3. **Служба** регистрирует приложение в базе при первом появлении (`Applications`), складывает секунды
   в накопителе (`ActivityAccumulator`) и раз в `FlushSeconds` пишет их в SQLite, реза по границам
   локальных часов — поэтому график «по часам» строится одним `GROUP BY HourIndex`.
4. **Workflow-движок** раз в `EvaluationSeconds` считает использование лимитов, записывает события
   превышения (по одному на пересечение порога за сутки) и выполняет действия правил реакции.
5. **Web-панель** забирает готовые ответы REST API (`/api/dashboard` и др.).

## Хранение

SQLite в режиме WAL, `busy_timeout=5000`, `synchronous=NORMAL`. Основные таблицы:

* `Applications` — приложения (создаются автоматически при первом появлении, ключ — имя+путь процесса);
* `ActivityIntervals` — активное время: приложение, сеанс, пользователь, локальный день, час, начало, конец, секунды;
* `Groups`, `GroupMembers` — группы приложений;
* `CriticalRules` — суточные лимиты (на приложение или группу, с днями недели и важностью);
* `WorkflowRules`, `WorkflowEvents` — правила реакции и журнал событий;
* `Sessions` — сеансы, из которых приходили данные;
* `Settings` — параметры учёта, изменяемые из панели.

Обслуживание: раз в 6 часов удаляются интервалы и события старше `RetentionDays`, а также приложения,
не встречавшиеся 30 дней.

## Нагрузка на ЦП

* Агент: крючок (событийный, без опроса), один таймер на сеанс, чтение активного окна и времени
  простоя — доли миллисекунды на такт. Измерено: **0.03–0.07 % ЦП**, ~45 МБ памяти.
* Служба: приём небольших JSON-отчётов, запись в SQLite пачками по таймеру и раз в минуту расчёт правил
  по агрегатам. Измерено: **0.03–0.08 % ЦП** в установившемся режиме.
* Интервал опроса настраивается из панели; на точность влияет соотношение N (окно активности)
  и интервала опроса.

## Отказоустойчивость

* Агент при недоступности службы копит выборки в буфере (до 2000) и повторяет отправку; после
  30 неудачных попыток подряд завершается, чтобы не остаться «осиротевшим» процессом.
* Служба перезапускает агента, если тот молчит дольше `AgentStaleSeconds`.
* Накопленные, но ещё не записанные секунды сбрасываются в базу при остановке службы.
* Служба создаётся с перезапуском при сбое (три попытки с интервалом в минуту).

## Безопасность

* Ключ агентов (`X-AppActive-Key`) генерируется автоматически и передаётся агенту в его файле конфигурации;
  без ключа приём данных недоступен.
* Изменения через API разрешены только с loopback, если не задан `AppActive:Security:AdminKey`;
  с заданным ключом — с любой машины (ключ сравнивается за постоянное время).
* Каталог данных закрыт правами SYSTEM и администраторов; подкаталог `agents` доступен пользователям
  только на чтение/запись своих конфигураций агента.
* Заголовки окон собираются по настройке `collectWindowTitles` (могут содержать чувствительные данные) —
  их можно отключить в панели.
* Действия Workflow типа `script` по умолчанию запрещены (`AppActive:Workflow:AllowScriptActions=false`).
