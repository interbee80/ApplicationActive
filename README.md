# ApplicationActive — учёт активности приложений в сеансах Windows

Служба Windows (запускается от имени **SYSTEM** при старте системы) следит за активными приложениями
во **всех** пользовательских сеансах, складывает данные в **SQLite** и отдаёт Web-панель с REST API:
активность по часам, топ приложений, критическое время за сутки по приложению или группе, workflow-правила
и диагностика нагрузки.

```
                 сеанс пользователя №1      сеанс пользователя №2
                 ┌───────────────────┐      ┌───────────────────┐
                 │ AppActive.Agent   │      │ AppActive.Agent   │   ← по процессу на сеанс
                 │ крючок активного  │      │                   │
                 │ окна + простой    │      │                   │
                 └─────────┬─────────┘      └─────────┬─────────┘
                           │  HTTP на loopback (порт из appsettings.json)
                           ▼                          ▼
        ┌──────────────────────────────────────────────────────────────┐
        │ AppActive.Service (LocalSystem, автозапуск)                  │
        │  • супервизор сеансов (WTS) и запуск агентов                 │
        │  • приём отчётов, накопление и запись в SQLite (WAL)         │
        │  • Workflow-движок: критическое время, события, скрипты, hook│
        │  • Kestrel: REST API + Web-панель + статика                  │
        └──────────────────────────────────────────────────────────────┘
                           │
                           ▼
                  %ProgramData%\AppActive\activity.db
```

## Как считается активность

Приложение считается активным, если **активно его окно** и **в течение N секунд была активность клавиатуры или мыши**.

* Агент получает точные моменты переключения окон через крючок `EVENT_SYSTEM_FOREGROUND`
  и раз в *интервал опроса* снимает состояние (`GetForegroundWindow`, `GetLastInputInfo`).
* За такт засчитывается промежуток **от начала отрезка до момента последнего ввода**:
  при непрерывной работе это почти весь такт, при разовом нажатии в начале такта — почти ноль,
  а при простое дольше N секунд — ноль.
* Экран входа и блокировки (`LogonUI.exe`, `LockApp.exe`) не учитываются.
* Служба складывает секунды в интервалы, режет их по границам локальных часов и сбрасывает в SQLite
  пачкой (по умолчанию раз в 15 с) — вместо тысяч мелких строк получаются длинные отрезки.
* Нагрузка: один такт — это чтение активного окна и времени простоя (доли миллисекунды).
  На этой машине измерено: **агент 0.03–0.07 % ЦП, служба 0.03–0.08 % ЦП** при интервале 3–5 с.

Точность максимальна, когда **N ≈ интервал опроса**. Если N заметно больше интервала, короткие паузы
между действиями пользователя считаются активностью.

## Единая точка настройки

Все параметры задаются **только** в `src\AppActive.Service\appsettings.json` (рядом с исполняемым файлом
после установки). В коде нет «запасных» значений — при незаполненной конфигурации служба не стартует
и печатает, что именно не задано.

| Параметр | Назначение | Значение в поставке |
|---|---|---|
| `AppActive:Urls` | адрес и **порт** Web-панели (единственное место, где задаётся порт) | `http://127.0.0.1:5190` |
| `AppActive:DataDirectory` | каталог данных (поддерживает `%ПЕРЕМЕННЫЕ%`) | `%ProgramData%\AppActive` |
| `AppActive:DatabaseFileName` | имя файла базы SQLite | `activity.db` |
| `AppActive:ServiceName` | имя службы в диспетчере служб | `AppActive` |
| `AppActive:Security:AdminKey` | ключ для изменений из Web-панели; пусто — изменения только с этой машины | пусто |
| `AppActive:Security:IngestKey` | ключ агентов; пусто — генерируется автоматически | пусто |
| `AppActive:Security:AllowRemoteRead` | разрешить чтение API с других машин | `true` |
| `AppActive:Monitoring:Enabled` | включён ли мониторинг сеансов | `true` |
| `AppActive:Monitoring:LaunchAgents` | запускать агентов в сеансах | `true` |
| `AppActive:Monitoring:SessionScanSeconds` | период сканирования списка сеансов | `10` |
| `AppActive:Monitoring:AgentStaleSeconds` | через сколько секунд молчания агент считается зависшим | `180` |
| `AppActive:Monitoring:Initial:*` | начальные значения параметров учёта (только для новой базы) | см. файл |
| `AppActive:Workflow:AllowScriptActions` | разрешить действия `script` в workflow | `false` |
| `AppActive:Logging:Level` | уровень журнала (`debug`, `information`, `warning`, `error`) | `Information` |
| `AppActive:Logging:FileRetentionDays` | сколько дней хранить журналы | `14` |

Параметры учёта из `Monitoring:Initial` (интервал опроса, N, частота сброса, хранение, игнорируемые процессы)
применяются **один раз — при создании базы**; дальше они меняются из Web-панели и хранятся в базе.
Значения из базы всегда приоритетнее файла.

Переопределить адрес разово можно ключами `--urls`/`--port` (скрипт печатает предупреждение — это аварийный вариант).

### Открыть панель с других машин

1. В `appsettings.json`: `"Urls": [ "http://0.0.0.0:5190" ]`.
2. Задать `AppActive:Security:AdminKey` (иначе изменения будут доступны только с самой машины).
3. `scripts\install-service.ps1 -AddFirewallRule`.

## Сборка и установка

```powershell
# 1. Сборка и публикация (порт берётся из appsettings.json)
.\scripts\build.ps1 -Publish                 # требует установленного .NET 8
.\scripts\build.ps1 -Publish -SelfContained  # со средой выполнения .NET внутри

# 2. Установка службы (нужен PowerShell от имени администратора)
.\scripts\install-service.ps1                # копирует в C:\Program Files\AppActive, создаёт службу
.\scripts\install-service.ps1 -AddFirewallRule

# 3. Проверка
.\scripts\service-status.ps1

# 4. Удаление
.\scripts\uninstall-service.ps1              # -PurgeData -RemoveFiles -RemoveFirewallRule
```

Служба создаётся с типом запуска **автоматически**, учётной записью **LocalSystem** и перезапуском
при сбое (три попытки с интервалом в минуту).

> Если PowerShell отказывается запускать скрипты («running scripts is disabled on this system»),
> выполните один раз в текущем сеансе:
> `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force`
> (или запускайте так: `powershell -ExecutionPolicy Bypass -File .\scripts\install-service.ps1`).

### Запуск без установки (отладка)

```powershell
.\src\AppActive.Service\bin\Debug\net8.0\AppActive.Service.exe --console --data-dir .\.run\data
```

В консольном режиме без прав SYSTEM агент запускается в текущем сеансе через обычный запуск процесса —
этого достаточно, чтобы проверить весь конвейер: окно → агент → база → панель.

## Команды службы

| Команда | Что делает |
|---|---|
| `AppActive.Service.exe` | запуск как службы Windows (если процесс запущен не через диспетчер служб — работает в консоли) |
| `--console` | принудительный консольный режим |
| `--service` | принудительный режим службы |
| `--self-test` | самопроверка ядра: схема, автосоздание приложений, разбиение по часам, лимиты, события, dashboard |
| `--seed-demo [дни]` | заполнить базу демонстрационными данными |
| `--data-dir <путь>`, `--urls`, `--port`, `--no-monitor` | разовые переопределения для отладки |
| `AppActive.Agent.exe --self-test` | проверка правила учёта активности на синтетических данных |
| `AppActive.Agent.exe --once` | один такт учёта (диагностика) |

## Web-панель

`http://127.0.0.1:5190` — разделы: **Обзор** (KPI, график по времени, лента дня, топ приложений, пользователи,
события), **Критическое время**, **Группы**, **Workflow**, **Настройки**, **Диагностика**.

REST API описан в [docs/API.md](docs/API.md), архитектура — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

### Цвета приложений

Каждому приложению служба назначает цвет из палитры (`appColors` в ответе `/api/dashboard`), поэтому оно
окрашено одинаково **везде**: в столбцах графика, в легенде, в ленте дня, в маркерах таблицы и в чипах
групп. Верхние по времени приложения получают максимально различимые цвета.

### Выбор периода

Над графиком — панель периода:

* быстрые кнопки: 30 мин, 1 ч, 6 ч, 24 ч, 7 дн, 30 дн, «Сегодня», «Вчера»;
* поля «С» и «По» в формате Grafana: `now`, `now-1h`, `now+30m`, `now-7d`, `now-1h30m`, `today`,
  `yesterday`, `2026-10-06`, `2026-10-06T10:30`;
* **выделение участка мышью прямо на графике** — период заполняется по выделенным столбцам;
* период и дата пишутся в адрес страницы (`?from=now-7d&to=now`) — ссылку можно сохранить в закладки.

До 48 часов график строится по часам, дольше — по суткам; лента дня масштабируется под выбранный период;
CSV-выгрузка учитывает период.

### Работа с процессами

В таблице приложений кнопка **«процессы»** открывает список процессов этого приложения во всех сеансах
(с сеансом, PID, памятью и временем запуска) и позволяет завершить один процесс или все сразу.
Завершение выполняется службой от имени SYSTEM, поэтому работает и для приложений других пользователей.
Системные процессы (`csrss`, `winlogon`, `services`, `lsass`, `svchost`, `dwm` и процессы самой службы)
защищены — их завершить нельзя. Каждое завершение попадает в журнал событий и видно в ленте.

## Критическое время

Правило задаёт суточный лимит **для приложения или для группы**: например, «Chrome — не больше 2 часов»
или «Браузеры — не больше 3 часов». Панель показывает прогресс, остаток («осталось 42 мин») и превышение.
При пересечении порога (100 %, 200 % …) в журнал пишется событие; правила реакции может добавить
запуск скрипта или webhook.

## Диагностика нагрузки

`GET /api/diagnostics` и раздел «Диагностика» показывают загрузку ЦП и память службы и каждого агента,
счётчики приёма, размер базы, число интервалов за сутки и время последнего сброса — этого достаточно,
чтобы убедиться, что учёт не нагружает машину.

## Требования

* Windows 10/11 или Windows Server 2016+ (нужны WTS API и `GetLastInputInfo`).
* Установленный .NET 8 (или публикация `-SelfContained`).
* Права администратора — только для установки службы.

## Сборка без интернета

В `nuget.config` первым источником подключён локальный каталог `.packages`, поэтому сборка не обращается
к nuget.org. Если пакетов не хватает (ошибка `NU1101`), выполните один раз:

```powershell
.\scripts\setup-offline-packages.ps1   # копирует нужные пакеты из кэша %USERPROFILE%\.nuget\packages
```

В ограниченных окружениях (песочницы, CI) многопроцессная сборка MSBuild может падать без сообщений —
скрипт `build.ps1` по умолчанию собирает в один процесс (`-m:1`); ключ `-Parallel` возвращает обычное поведение.
